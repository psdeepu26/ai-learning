KV Cache: The Secret Memory Trick That Makes LLMs Fast

June 23, 2026 · Tuesday · AI Learning
🧒 Like you're 5

Imagine you're writing a story, one word at a time. Every time you add a new word, you re-read the entire story from the beginning to remember what you've already written. That would take forever.


A KV Cache is like keeping sticky notes summarizing everything you've written so far. When you add a new word, you just glance at the sticky notes instead of re-reading the whole story. It's the reason an LLM can generate 10,000 words without getting exponentially slower.

🔧 For the engineer

What KV Cache actually stores

During autoregressive decoding, each token attends to all previous tokens via multi-head attention. The Key (K) and Value (V) projections for each layer are computed at generation time and cached. The Query (Q) is only computed for the current token — the heavy lifting of previous tokens is already cached.

# Pseudo-compute for decoding step t
for layer in range(num_layers):
    q = compute_q(hidden_states[t])            # only current token
    k_cache, v_cache = kv_caches[layer]         # all previous tokens
    attn = softmax(q @ k_cache.T / sqrt(dim))
    out = attn @ v_cache
    # Append current KV to cache
    kv_caches[layer].append(compute_kv(hidden_states[t]))

Memory cost: the bottleneck

KV Cache is the dominant memory consumer at inference time. For a model with L layers, H attention heads, sequence length S, and head dimension D_h:

KV_cache_size = 2 × L × H × S × D_h × bytes_per_element
# Example: Llama 70B, L=80, H=64, S=32768, D_h=128, fp16
# = 2 × 80 × 64 × 32768 × 128 × 2 bytes
# ≈ 8.9 GB just for KV cache per request!

This is why GPU memory limits batch size and sequence length — a critical concern when deploying NVCF or any production LLM service.

Multi-Query & Grouped-Query Attention (MQA / GQA)

To reduce KV Cache memory, modern architectures share key/value heads across query heads:

# Multi-head attention: Q_heads=32, K_heads=32, V_heads=32  (full KV cache)
# Multi-query:         Q_heads=32, K_heads=1,  V_heads=1   (32× reduction)
# Grouped-query:       Q_heads=32, K_heads=4,  V_heads=4   (8× reduction)

# Llama 3 70B uses GQA with 8 KV heads — dramatic memory savings
# with minimal quality loss

What this means for SRE / production deployments

  • vLLM and TensorRT-LLM both implement paged KV cache (like virtual memory) to reduce waste from fragmentation
  • Prefix caching — if multiple requests share a common prompt prefix, the KV cache for that prefix is computed once and reused (massive savings for system prompts or RAG contexts)
  • Offloading — tools like SGLang can spill KV cache to CPU memory for very long contexts
  • Monitor GPU memory utilization as your proxy for KV cache pressure — it's the canary in the coal mine for capacity planning
⚡ Micro-action (5 minutes)

Run this quick check to see how much GPU memory your model's KV cache would consume at different sequence lengths:

# Quick back-of-the-envelope KV cache calculator
python3 -c "
L, H, D_h, dtype_bytes = 80, 64, 128, 2  # Llama 80B-like
for ctx_len in [2048, 4096, 8192, 16384]:
    size_gb = (2 * L * H * ctx_len * D_h * dtype_bytes) / (1024**3)
    print(f'  ctx={ctx_len:>6} → KV cache ≈ {size_gb:.2f} GB')
"

Compare the result to your GPU memory. If a single 16K-context request uses 4+ GB just for KV cache on a 40 GB A100, you know exactly why batch size drops at long contexts.
